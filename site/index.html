The problem

Every normal way to give an agent a secret leaks it.

AI coding agents run commands for you — deploys, migrations, API calls, git push. Those commands need credentials, and a password manager's job ends the moment it hands the value over. Once a value is in an agent's context, it has leaked.

.env files & key folders

Sit in plain text next to your code. Agents read them, quote them back, sometimes commit them.

Pasting into the chat

Lands in conversation history, in logs, and wherever that chat is stored or synced.

Exported env vars

Reach every process you start — an agent that runs env prints them all.

Command output

curl -v, debug logs and errors echo tokens straight into the agent's context.

No record or control

You can't see which agent used which credential, or say "ask me first for production".

How it works

Keylo hands the value to the command, never to the agent.

Say you've saved your production database login as a secret named prod-db, and you ask Claude Code to run npm run migrate, which reads DATABASE_URL:

The agent finds the secret by name, never by value. search_secrets returns prod-db, its type and field names, and whether the key can use it.

The agent asks Keylo to run the command, mapping a variable to a secret: run_with_secrets with {"DATABASE_URL": "prod-db:connection_string"}.

Keylo checks the agent's access key. If prod-db is out of scope, an approval window opens, confirmed with Windows Hello, Touch ID or your system password.

Keylo starts the command with the value in DATABASE_URL. If the value appears in output, it's replaced with [keylo:prod-db] before the agent sees it.

The use is written to an audit log, with the key, the secret and the process that asked.

Injection tools value injected

1Password SDKs, Vault, Doppler, .env loaders: the real value is placed into the agent at runtime.

Keylo run-only

The agent names a secret; Keylo runs the command with it and returns only redacted output.

Keylo vs. secret injection

Injection hands over the value. Keylo doesn't.

Most developer secret tools improve on plaintext .env files by injecting the value at runtime. Only Keylo keeps the value out of the agent's context entirely.

Features

Everything your agents need — and everything you do.

For agents run-only

  • MCP server (keylo mcp): search secrets, list types, run commands with secrets, request access, browse AWS Secrets Manager.
  • Per-agent access keys covering chosen categories/secrets or everything, with optional expiry — stored only as SHA-256 hashes.
  • Approvals for anything out of scope: Deny, Allow once, or Always allow — each confirmed with your identity check.
  • Output redaction of every value a command received, including values from earlier commands.
  • "Always ask" environments: production secrets need approval every time, whatever the key covers.
  • Audit log of every agent use, with the calling process chain.
  • One-step Claude Code setup: keylo keys create … --add-to-claude, or a button in the app.

For you desktop + CLI

  • Desktop app for Windows, macOS and Linux, plus a CLI that does everything the app does.
  • 14 built-in secret types (login, API key, database, SSH key, note, credit card, bank account…) plus your own custom types with named fields.
  • Linked secrets: read items live from 1Password or AWS Secrets Manager, with per-environment links (orders-db@prod).
  • Import files, folders, and CSV exports from Chrome, Bitwarden, 1Password, LastPass, KeePassXC, Apple Passwords — and export back out, so you're never locked in.
  • Optional master passphrase (Argon2id), unlocked with Windows Hello (TPM) or Touch ID (Secure Enclave).
  • Sync across your own devices through any folder (OneDrive, iCloud, Dropbox) — end-to-end encrypted, the service never sees a value.

Security model

Encrypted at rest, sealed by the OS, auditable by you.

Secret values live in Keylo's vault, each encrypted (AES-256-GCM) under a key the operating system protects. Details and the whole vault are authenticated, so tampering is detected.

WindowsDPAPI, tied to your Windows account

Optional master passphrase (Windows & macOS) wraps the key a second way, so a copied disk can't be opened without it.

What Keylo protects against

  • Agents seeing values — they get redacted output, never the value.
  • Agents using secrets they shouldn't — access keys, approvals, "always ask" environments.
  • Secrets in plaintext files getting committed, synced or shared.
  • Other users on the same computer.
  • A stolen or copied disk, or a backup, without your account password.
  • The sync folder & its service — only encrypted files, changed files rejected.

Quick start

Three commands to agent-safe secrets.

1 · Add a secret (the value is prompted, never shown or kept in shell history)
# Add via the app, or the CLI:
keylo add github-token --type api_key
2 · Use it in a command — as an environment variable
keylo run --env GITHUB_TOKEN=github-token -- gh repo list

# A file-delivered credential (service-account JSON, kubeconfig, PEM):
keylo run --file GOOGLE_APPLICATION_CREDENTIALS=google-oauth -- gcloud auth activate-service-account
3 · Give Claude Code its own access key (covers the "dev" category) and register Keylo
keylo keys create "Claude Code" --category dev --add-to-claude

# ...or by hand, keeping the key in your user settings:
claude mcp add keylo --scope user --env KEYLO_ACCESS_KEY=kyl_… -- "/path/to/keylo" mcp

Honest limits

What Keylo doesn't claim.

Keylo fails closed and documents its edges — that candor is what makes the rest trustworthy.

  • Not a team platform. No fleet-wide discovery, SSO/SCIM, or SIEM. For org-wide governance, an injection platform is the right tool.
  • Redaction catches accidents, not intent. A command that transforms a value (base64, hashing) can get it past the redactor. Access keys and approval are the real control.
  • An approved command gets the real value. Keylo stops the agent reading secrets, not a command you chose to run. Don't approve commands you don't understand.
